# v3.0.4 legacy cloud cutover — review only

No production migration or deployment is authorized by the repair task. The SQL
was generated with Supabase CLI `migration new` and tested against a disposable
PostgreSQL 17 / GoTrue / PostgREST backend on loopback. This does not establish
production schema, policy, grant, Auth, billing or infrastructure parity.

## Compatibility blocker

v3.0.3 issues unconditional INSERT/PATCH requests, without a revision. A client
update alone cannot make those existing installed clients safe. The migration
atomically introduces the new RPC **and removes authenticated direct write
privileges** on `public.bvom_data`, including column privileges. Old clients can
still read/restore their own cloud document and record/export locally, but their
cloud uploads fail. Updating the installed client enables the revisioned writer.

This is a genuine cloud-write compatibility break, requiring an owner-approved
cutover and communication/update plan before production. It is not represented
as a transparent backward-compatible migration. A v3.0.4 client without the
migration also fails closed for cloud writes. Do not fall back to old PATCH.

BB2's `public.bvom_cloud_state`, revision protocol, RLS and sidecar modules are
unchanged. Its existing shared-legacy conflict guards still apply.

## Review before any production change

1. Compare the actual production `bvom_data` columns, owners, constraints,
   triggers, policies, grants (including inherited/column grants), API exposed
   schemas and role memberships with the disposable fixture. Verify the
   function owner is a trusted database migration role, never `authenticated`.
2. Confirm `id` is a bigint-compatible stable identifier; review duplicate
   documents, their `created_at` ordering and the deterministic `id` tie break.
   The migration neither deletes duplicates nor rewrites JSON documents.
3. Take a verified database backup and owner-independent recovery export.
   Record row counts and data digests. Test recovery in an isolated environment.
4. Review the SECURITY DEFINER function: empty search path, fully qualified
   table/auth access, explicit `auth.uid() = p_owner_id`, no caller-supplied
   table/SQL identifiers, no PUBLIC/anon execution grant. Its privileged scope
   is the caller's latest legacy document only.
5. Run all real authenticated CAS/browser proofs against a fresh isolated
   Supabase project matching production's schema and policies. Do not use the
   owner's account, production documents, or the unrelated LEAKwise project.

## Explicit deployment sequence (owner action only)

1. Approve the old-client cloud-write interruption; arrange client update and
   clear user guidance to export local backups before resolving conflicts.
2. Provision/configure a separate hosted test backend and Netlify test site.
   Run the migration and test package there; verify Auth redirect URLs, RLS,
   cloud races, offline recovery, backup restore, old/new client coexistence
   and physical installed PWA acceptance. Local proofs are supporting evidence.
3. Re-review the final SQL and grants against production. In a planned cutover,
   apply `supabase/migrations/20261115203345_legacy_history_compare_and_swap.sql`
   as one transaction using the authorized migration operator. Do not split
   RPC publication from the direct-write fence. Migration exceptions roll the
   transaction back, including detection of inherited write privileges.
4. Verify SELECT still honors account RLS, authenticated INSERT/PATCH fail,
   anon RPC fails, owner RPC succeeds and two simultaneous CAS requests yield
   exactly one winner. Test with specifically authorized disposable accounts.
5. Publish the approved v3.0.4 client separately. Existing v3.0.3 cloud writes
   remain blocked until clients update. Local training/export remains available.
6. Verify restored/updated clients, durable loser exports, BB2 sidecar revisions,
   History and installed-PWA update behavior before declaring release GO.

## Failure / rollback

If client deployment fails after the database cutover, keep the direct-write
fence and restore the prior static client only as an explicitly limited local
training/read/export fallback. Re-enabling unguarded writes restores A02 and is
not a safe routine rollback. Keep the revision columns, trigger and RPC while
diagnosing; they do not rewrite existing JSON data. Database recovery, any
privilege restoration or schema rollback requires a separate owner decision.

## Protocol

`bvom_legacy_cloud_commit_v1(owner, expected_id, expected_revision, data,
request_id)` takes an owner-scoped transaction advisory lock (also covering
concurrent first inserts), locks the latest owned row and compares both id and
revision. The server returns `committed` with a revision or `conflict`; HTTP 200
alone does not mean synchronization succeeded. Retries with the same request id
are idempotent only for the identical latest payload. After a newer write, the
old request conflicts. A trigger increments the revision for trusted maintenance
updates too. The app retains local data on rejection or an unknown outcome.

Automatic uploads retain the existing fingerprint baseline checks and use CAS
for the final write. SYNC NOW cannot silently adopt a changed remote baseline.
KEEP THIS DEVICE explicitly resolves an already displayed conflict, still using
CAS. Export both devices before choosing a whole-document replacement; the
protocol detects conflicts rather than pretending to merge divergent histories.
